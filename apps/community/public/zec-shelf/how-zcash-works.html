01 / THE IDEA

Verification does not have to mean visibility.

A transparent chain lets everyone verify by exposing the transaction history. Zcash keeps public verification and replaces the exposed facts with cryptographic evidence. The network can reject counterfeits and double-spends without receiving the sender, recipient, or shielded amount.

The missing link

Privacy is the outcome. A receiver—the payment destination inside an address—is how the wallet gets there.

The comparison above asks what the ledger reveals after a payment is made. Before building that payment, the wallet must choose which Zcash transaction system to use. Transparent value and shielded value live in separate pools, and the recipient’s address tells the wallet which receiver types that destination accepts.

First: what is a pool?

A pool is a protocol-defined way of representing and moving the same ZEC. Each pool has its own transaction format, receiver type, and on-chain data structures. It is not a separate coin, account, or wallet.

Orchard balances were not moved automatically, do not expire, and remain under their owners’ control. 02 / SHARED ORDER

The chain is an ordered history and a shared clock.

Transactions propagate to nodes, wait in local mempools, and become settled history when miners include them in blocks. Each block points to the previous block. Its height is its position in the one agreed sequence; later blocks add confirmations and make reversal harder.

First · the reusable hash-function idea

A fingerprint binds bytes to a compact result.

A cryptographic hash maps any input to a fixed-size digest. Repeating the same operation gives the same result; changing even a tiny part of the input should change the digest unpredictably; and the digest should not reveal a practical route back to the input. Zcash uses several purpose-built hash constructions—not one universal function—for block links, commitments, tree nodes, nullifiers, transaction digests, key derivation, and proof transcripts.

Then · proof of work

A miner searches for a block header the network will accept.

A miner assembles a candidate block, including transactions from its mempool, and commits to that candidate in a header. Most header fields stay fixed while the miner varies a nonce and computes trial results. Because each result is unpredictable, the practical strategy is repeated search—not solving backward from the target.

03 / PRIVATE VALUE

A shielded balance is a collection of notes.

Wallets do not update a private “account balance” on-chain. They control discrete notes. Spending consumes selected notes completely, then creates new notes for the recipient and any change. Your displayed balance is a wallet-side sum of the unspent notes it can decrypt.

04 / SEALED RECORDS

The note stays private. Its commitment goes public.

A note contains an address, value, and randomness. The chain records a binding commitment to those contents and an encrypted payload for the recipient—not the plaintext note. Alice encrypts that payload using the public receiving key in Bob’s shielded receiver. Bob later combines the incoming viewing key (IVK) introduced above with the transaction’s public ephemeral key to decrypt it. The commitment and encryption do different jobs.

05 / MEMBERSHIP

Every commitment joins one append-only tree.

Nodes append note commitments in chain order and hash upward to a compact root. A wallet can prove one commitment belongs to that tree using only its Merkle path. The root used by a transaction is its anchor: a public fingerprint of a particular tree state, not an identifier for the hidden note.

06 / NO REPLAY

A nullifier says “spent” without saying which note.

To spend a shielded note, its owner proves authorization and derives that note’s unique nullifier with a keyed pseudo-random function: secret nullifier key material plus note-specific data produces a deterministic, one-time-looking serial. It is not a raw public hash of the commitment. The spend publishes the nullifier, so accepting it marks the note as spent without removing—or publicly identifying—its commitment in the tree. Nodes reject any later transaction that publishes the same nullifier, while observers cannot reverse the nullifier to discover which commitment was spent.

07 / CAPABILITIES

Keys separate spending, seeing, and receiving.

Zcash key material is a hierarchy of capabilities. A spending key authorizes value movement. Viewing keys are wallet secrets by default: they reveal selected transaction information but never authorize spending. An owner can voluntarily disclose a viewing key when they want another party to receive that key’s read-only access. Diversified addresses let one wallet receive at many unlinkable-looking destinations.

08 / DISCOVERY

A wallet finds money by trying to decrypt outputs.

Shielded outputs contain no searchable plaintext address. A wallet downloads compact chain data and attempts trial decryption with its incoming viewing key. Almost every attempt fails. A success reveals the private note, which the wallet verifies against the public commitment and records with its position for a future Merkle path.

09 / ZERO KNOWLEDGE

The proof compresses a private valid story.

The wallet’s secret inputs—notes, keys, Merkle paths, and randomness—are collectively called the witness. Zcash checks them with a circuit: not electronic hardware, but a fixed mathematical rulebook for a valid shielded transaction. That rulebook checks that inputs exist, the spender controls them, nullifiers are correct, and value balances. A compact proof convinces nodes that a valid witness exists while the witness itself stays private.

Before proving · Fiat–Shamir transcript

Hashing replaces the verifier’s live questions.

An interactive proof would alternate between prover messages and fresh questions from a verifier. Halo 2 instead records public inputs and proof messages in an ordered transcript, then hashes the transcript-so-far into each next challenge. A verifier later replays the same bytes and derives the same challenges without contacting the prover.

10 / PUBLIC PACKAGE

Ironwood reuses Orchard’s paired Action structure.

An Ironwood transaction uses the Orchard Action shape: each Action pairs one spend side with one output side. When the real counts differ, dummy components fill the shape. The pairing does not mean one input “became” one output; value conservation is enforced across the whole transaction. The public package contains opaque commitments, nullifiers, randomized authorization data, ciphertexts, an anchor, a proof, and a binding signature.

11 / END TO END

One send crosses a private lane and a public lane.

Most of the work happens inside the wallet: select notes, fetch paths, derive nullifiers, create outputs, encrypt, and prove. The network never repeats those private computations. It checks the public proof and state rules, orders the transaction, then publishes new commitments and nullifiers for wallets to scan.

12 / SETTLEMENT

Proof creation, broadcast, and confirmation are different events.

Proving is private local computation. Broadcasting sends the finished public transaction to a node. Nodes check it before holding and relaying it; a miner later includes it in a block. Inclusion updates the commitment tree and nullifier set. Confirmations describe how much chain has accumulated above that state change.

13 / BOUNDARIES

Shielded privacy is powerful, specific, and not magical.

The protocol hides shielded senders, recipients, note values, and the link between a spent note’s commitment and nullifier. The chain still shows that a transaction exists, when it was mined, its public fee, and its opaque fields. Network observers may see traffic outside the cryptographic protocol. Optional viewing keys support selective accountability without making everyone’s ledger public.

The formal model is tied to the verifier Ironwood actually runs.

The Rust verifier’s final multi-scalar multiplication is represented as a symbolic fingerprint. Captured one- and multi-Action executions are checked against that formal object so the proof is about the deployed verification path, not merely a similar protocol sketched on paper.

14 / EVOLUTION

The cryptography evolves; the mental model endures.

Zcash moved from research proposals to Sprout, Sapling, Orchard, and now Ironwood as proving became faster, mobile-friendly, and free of trusted setup. Upgrades can change pools, circuits, formats, and proof systems. The durable idea is unchanged: private notes, public commitments, unlinkable nullifiers, encrypted delivery, and proofs of valid state transitions.

15 / ROADMAP

Tachyon aims to make the private ledger compressible.

Tachyon is a proposed new Zcash shielded pool, independent of today’s Ironwood pool—not a feature running on mainnet today. It keeps the durable model of private notes and public validity proofs, but redesigns the protocol around proof-carrying data so prior verified work can be compressed and carried forward. The target is to reduce per-transaction proof overhead, aggregate validation work, and stop the active nullifier state from growing forever without weakening shielded privacy.

Proposed
Active development, not an activation promise

As of July 28, 2026, Ragu and the Tachyon protocol are under construction. Testnet work, optimization, security review, a Zcash Improvement Proposal, and community consensus are gates before any mainnet activation.

Before the demos · PCD primer

A proof that can absorb earlier proofs.

Proof-carrying data (PCD) lets each step prove both its new work and the validity already established by earlier steps. Think of a running, tamper-evident receipt: it can summarize a growing history without making every verifier replay that whole history. Tachyon’s Ragu library is being built to provide this recursive proof machinery without a trusted setup.

The whole mechanism in six moves.

Zcash is not an invisible ledger. It is a public ledger of cryptographic state transitions whose private facts remain with the participants.

01Wallets hold capabilities

Keys let a wallet receive, see, disclose, or spend.

02Value lives in notes

Spends consume old notes and create fresh ones.

03Commitments enter the tree

The public root summarizes private-note commitments.

04Nullifiers stop replay

A unique public serial is unlinkable to the spent leaf.

05A proof enforces the rules

Existence, control, correctness, and balance—without the witness.

06The chain orders the result

New commitments and nullifiers become shared state for the next send.
