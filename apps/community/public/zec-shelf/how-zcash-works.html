An interactive tour of the concepts behind the Orchard → Ironwood pool migration: why a background wallet must sync, what an anchor really is, why proving and broadcasting are two different operations, and how sync timing can betray a wallet — or protect it. Everything runs locally, nothing leaves this page.

01The chain as a clock

The blockchain is a sequence of blocks; height is simply a block's position in that sequence. A new block is mined roughly every 75 seconds, no matter what's inside it — so height doubles as the network's shared clock. "Height 3,500,048" is not just a place in the data, it is a point in time everyone can compute. The tip is the newest block.

Takeaway: height = time. Any future height will inevitably arrive, at a predictable moment — you can schedule against it like a calendar.

02The note commitment tree

Every shielded note ever created adds one leaf to a single, giant Merkle tree. The leaf (the note's commitment) is public on the chain — only the note's contents are encrypted. Because every node is the hash of its children, the root is a fingerprint of every note so far: append one leaf and the hashes change all the way up ("running hash"). Really this is an append-only list with a hash pyramid built over it — notes live only in the bottom row; the internal nodes store nothing (they are computed hashes, and above empty regions they are fixed "empty" constants). When they flash after an append, they are being recomputed, not written to. The tree is a pure function of public chain data, so everyone computes the exact same tree — what's private is only knowing which leaves are yours.

Takeaway: there is no "your tree" and "my tree" — one shared tree, one shared root per height. Private is only the knowledge of ownership (and your notes' Merkle paths).

2bThe chain feeds the tree

The bridge between the last two sections: the tree is not a separate world — it is derived from the chain, block by block. Each block carries transactions; their shielded outputs are note commitments, and mining the block appends them to the tree in chain order, producing the next version of the one shared tree — and its root, stamped against that height. A transparent-only block appends nothing: the root is simply inherited. Think git: block = commit, root = SHA — one repository, every clone identical, older states are prefixes of newer ones.

Takeaway: not "each block has its own tree" — each block has its own version of the same tree. The append order is fixed by the chain, so everyone builds a bit-identical structure; the stamped roots are exactly the anchors of the next section.

2cThe frontier — what a checkpoint actually stores

Because the leaf row fills strictly left → right, the tree is always three territories: a frozen left region (subtrees over fully-filled leaf ranges — nothing can ever change them again, so each is summarized by a single hash), an empty right region (nodes there are globally known constants that nobody stores), and the seam between them — the only live part. The frontier is that seam written down: the newest leaf plus, per level, the hash of the full left-sibling subtree beside the path (an "ommer") — at most one per level, so ≤ 33 values for a depth-32 tree with billions of leaves. It is enough to append forever and compute every future root. It is not enough to build witnesses for old notes — but pre-birthday notes can't be yours, which is exactly why restore (section 04) works from a bundled checkpoint.

Takeaway: a checkpoint is kilobytes, not gigabytes — because it is a frontier, not a copy of the tree. The past is frozen, the future is constants; only the seam needs carrying.

03Roots history = anchors

The root changes with every block, so history is a sequence of roots, one per height — and each one is frozen forever the moment its block is mined. An anchor is simply one root picked from this shared history. A spend proof says: "my note is a leaf in the tree with THIS root" — which also reveals the note existed before that height. Crucially, the V6 transaction format excludes the anchor from the signature (ZIP 374): you can sign a transaction today and install the anchor, witness and proof much later without breaking the signature.

Takeaway: an anchor is identified by a height — its value is unknown until that block is mined, but its future existence is guaranteed. That's why a plan can assign anchors ahead of time.

04Sync, checkpoints, pruning & retention

A light wallet scans blocks linearly, appending commitments to its local tree copy — it inevitably passes through every height, so an anchor can never be "missed", only "not reached yet". But it discards blocks after scanning: to use a past tree state it must have snapshotted it on the way through (a checkpoint). Normally only ~100 recent checkpoints survive (pruning); during a migration, checkpoints on the 144-grid are pinned forever so a transfer's anchor stays provable no matter how late the proof happens. Going backwards without a snapshot means an expensive replay. Restoring an old seed is the same machinery in reverse gear — switch the demo to Restore from seed: the wallet jumps to the nearest bundled checkpoint below your birthday, loads a log-size frontier instead of the whole tree (section 2c shows why that suffices), and trial-decrypts only from birth onwards.

Takeaway: the tree state at a height is captured going FORWARD, not derived backward. Sync early or sync late — both fine; what matters is that some sync passes the boundary, and retention keeps it usable forever.

05The 144 boundary grid & the anchor draw

The anchor in a transaction is public — a fresh one would timestamp exactly when your wallet proved (and therefore synced). So migration transfers may only anchor to a coarse shared grid: heights divisible by 144 (~3 h), called boundaries. The whole cohort draws from the same few values, so an anchor identifies nobody. The draw is randomized: the newest boundary is never used, age 1 is most likely, the mean is ~2 boundaries (~6 h), capped at ~16 (~2 days) — so the anchor's age says nothing about when you actually proved.

Takeaway: you don't want your anchor to be unique — you want it to be everyone's. Shared, coarse, randomly aged: maximum crowd, minimum signal.

06The migration plan

On confirmation the wallet first performs a note split — a shielded self-send inside Orchard that turns one fat note into standard-denomination notes: 1 | 2 | 5 × 10^k, largest first (like cash — 3.2 ZEC becomes 2 + 1 + 0.2), so everyone's transfers carry the same few amounts (crowd camouflage) and the note count follows from the balance. Then N pool-crossing transfers are planned: each gets a broadcast height S (Poisson-spread over ~a day, exponential gaps with mean 144 blocks) and an anchor boundary B drawn from the grid below its S. Everything is pre-signed at commit, anchor-less — the plan fixes the two heights, not the root values.

Takeaway: every transfer carries TWO heights: B (what to prove against) and S (when to send). B < S, both known from day one, both just points on the chain-clock.

07Prove vs broadcast — two decoupled operations

Once boundary B is mined and some sync has scanned past it, the transfer can be proved: install the real anchor + witness into the signed transaction and compute the ZK proof — pure local computation, zero network. That can happen any time between B settling and S. Broadcasting at S is then a single network submit of the stored bytes. Collapsing the two ("prove at broadcast time") is what forces a sync right next to a broadcast — the exact coupling the whole design exists to avoid. A 30–60 day expiry is the distant safety margin.

Takeaway: proof = local, whenever convenient. Broadcast = network, exactly at S, and nothing else. The broadcast window should contain one packet's worth of intent: the transaction itself.

08The privacy game: sync patterns vs. the observer

The lightwalletd server sees which wallet syncs when; the chain shows which anchor each migration tx used. The observer's question: "whose sync history is consistent with this tx?" — and your goal is to make the candidate set as large as possible. Compare three strategies: syncing only at your own boundaries (your sync schedule mirrors your plan), a dumb hourly cadence (everyone looks identical), and Vizor-style build-and-clump (everything linked at once). Because S − B ≥ 3 h by construction, any plan-independent cadence under 3 h guarantees every transfer is proved before it's due.

Takeaway: sync "exactly when needed" is maximally efficient and maximally identifying. Sync "often and blindly" carries zero information — frequency, not targeting, is what buys privacy.

09Due-ness & the estimated tip

A transfer is due when the chain reaches its S (and it's proved, its deps mined, not expired). The engine's clock for this is today the scanned tip — so a wallet with a stale sync doesn't even know a transfer is due, although the real network passed S long ago and the proof sits ready. But height is derivable from wall-clock: estimated height = last tip + elapsed/75 s. With estimated-height due-ness, a broadcast wake needs no network at all before the submit itself — the cleanest possible broadcast window.

Takeaway: sync answers "WHAT happened" (roots, witnesses, confirmations) — but "WHEN is it time" is just arithmetic. Only the former needs the network.

10Migration scenarios — how it all plays out

Everything above assembled into the actual Android design: two lanes. Lane A (hourly worker) syncs and proves — never broadcasts; Lane B (per-transfer worker) exclusively broadcasts — it checks a tri-state (READY / AWAITING_PROOF / NOTHING_DUE) against the estimated tip, defers while any sync is live, and when a transfer comes due unproven it silently shifts the plan forward (expiry untouched). Pick a scenario and press play: the happy path, every error case, and what the user actually sees. Shaded bands are the privacy buffers — no sync activity ever sits inside one. Use the platform toggle to compare with the expected iOS sibling design, which assumes no background execution at all: everything rides pre-scheduled local notifications — about two per transfer, a PROVE one after its boundary settles ("open to prepare") and a SEND one at Sᵢ — delivered by the system with zero app execution and adaptively re-armed or cancelled on every open. Sync and send stay separated by visit type: prove visits sync, send visits never do (the overdue gate holds sync). 5 transfers ≈ 10 notifications, fewer when one prove visit covers several settled boundaries.

Takeaway: one design, two platforms, fourteen fates — and in every single one either the migration completes, or the user is routed to an explicit screen with funds intact. Missed windows shift; detection happens during sync; notifications are shortcuts on Android and load-bearing on iOS — but progress never depends on background execution, and nothing is ever lost.
